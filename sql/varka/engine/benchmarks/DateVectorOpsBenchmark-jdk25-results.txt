================================================================================================
DateVectorOps kernels (JMH)
================================================================================================

The milestone-1 hand-written kernels (`DateVectorOps`, reference code for every later kernel)
against a scalar Java loop, over three row counts and two null patterns. See
DateVectorOpsBenchmark.java.

This file is the forked-JVM measurement that replaced the in-process (forks=0) run in git history
at 46339ca285d. That run measured the kernels on the surefire JVM after the JUnit suites had
shaped its profiles (m4/PLAN.md, debt register; VARKA-24.md section 6), and it
understated every vector kernel: vectorDateDiff NULL_FREE at 10000 rows read 431 ops/ms there
and reads 1211 here, the same figure VARKA-24 could only reach by forcing C2 to inline the Vector
API (1276). The scalar loops moved by about 10%. The narrow-width table is new; the earlier file
had none.

OpenJDK 64-Bit Server VM 25.0.4+7-1-26.04-Ubuntu on Linux 7.0.0-30-generic
AMD Ryzen AI 9 HX PRO 370 w/ Radeon 890M (AVX-512 on a 256-bit datapath), machine otherwise idle
JMH 1.37, throughput mode, forks=1 (one forked JVM per benchmark, launched from the surefire
JVM with its argLine; the narrow run's fork inherits -XX:MaxVectorSize=16), 1 thread,
2 x 500 ms warmup, 3 x 500 ms measurement. Higher is better.
Run: ./build/mvn -f sql/varka/engine/pom.xml test -Dvarka.jmh=true

--- Reading these numbers (ratios by minimum-of-3, vector against scalar) ---

* AVX-512, 10000 rows: addDays 3.75x null-free (590 against 157) and 3.6x mixed-null (477
  against 133); subDays the same; dateDiff 8.3x null-free (1211 against 145) and 6.2x
  mixed-null (792 against 128). At 1M rows, out of cache, 3.3x-3.4x for all three null-free.
  At 32 rows, 3.6x-4.9x: the per-call overhead is small enough that a single batch still pays.
* 128-bit, 10000 rows: addDays and subDays 1.29x-1.30x null-free (205 against 158) and 1.16x
  mixed-null; dateDiff does not win - 0.98x null-free (143 against 145) and 0.86x mixed-null
  (109 against 128). At 1M rows 1.13x-1.20x. At four lanes these kernels' per-group validity
  handling costs about what the lanes save, which is the milestone-4 validity work (VARKA-45
  to VARKA-47) in one number; the emitted kernels are measured separately in the catalyst parity
  file and are not this file's subject.
* The scalar loops are identical at both widths (157-158 null-free at 10000 rows), as they
  should be: the width flag changes nothing scalar code runs.
