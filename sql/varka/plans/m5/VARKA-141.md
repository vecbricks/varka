# VARKA-141: the module map claims Varka's own files

*Milestone 5, section 2.76. Opened and implemented 17 September 2026, from what
VARKA-123's first demonstration showed.*

## 1. Where this came from

VARKA-123 made `Check changes` diff the pull request's own files instead of this
fork's whole divergence from apache/spark, and its own run proved the base is
computed correctly. What it could not show from its own branch was the
narrowing, because two of its files were the test selector itself.

The first pull request opened after it merged - #234, VARKA-122 - is that
demonstration, and it came back half right. The gate printed `change detection
base: eb33fdd14b2` and `changed files vs base: 9`, its own files, against the
roughly 2100 the old reference gave. Then every module gate still answered true.

The cause is one step further on. Seven of those nine files map to narrow
modules; two - `sql/varka/coverage.json` and `sql/varka/emitted_bytes.json` -
live directly under `sql/varka/`, which no module claimed, so
`determine_modules_for_files` sent them to `root`, which means "test
everything". The base names the files correctly and the map then decides what
they mean.

## 2. The admission check, done

**Which files no module claims.** `sql/varka/papers/` is ignored, the plans,
skills and READMEs are `varka-docs`, `sql/varka/engine/` and `sql/varka/bench/`
are their own modules. What is left under `sql/varka/` is the two committed data
files, and under `dev/` the Varka shell scripts - the quote check and the table
of contents are already claimed by `varka-docs`, the rest are not.

**Where each belongs, from what reads it.** `coverage.json` is generated by
`VarkaCoverageSuite` and byte-compared by it, and read by
`VarkaCoverageDifferentialSuite` in `sql/core`; `emitted_bytes.json` is the
emitted-bytes oracle's committed digests, generated and compared in catalyst.
Both belong to catalyst, and `sql` depends on catalyst, so claiming them there
selects the differential too. `dev/varka_bench_*.sh` and `dev/varka_datapath.sh`
are the bench job's own tooling and belong to `varka-bench`.

**What is deliberately left at `root`.** The developer-only scripts -
`varka_gate.sh`, `varka_precommit.sh`, `varka_worktree.sh`, `varka_emit.sh` - are
run by people, not by any CI job. Claiming them for a module would say a job
tests them, which is false; ignoring them would say a change to them needs no
job, which is a stronger claim than this task can support. They stay where they
are until someone shows what they should select.

## 3. The design

Two regexes on the `catalyst` module for the data files, two on `varka-bench`
for the bench drivers. No change to the base computation, the workflow, or any
module's dependencies.

## 5. Tests, and what each is for

`dev/sparktestsupport/modules.py` carries doctests for `is_ignored_file`, and
the mapping is exercised by the measurement below over real file lists rather
than invented ones - the nine files of #234, a plan file alone, the surface
driver alone, and a results file alone.

## 6. The measurement

Module selection for four real changes, before and after:

| change | before | after |
| :--- | :--- | :--- |
| #234's nine files | `root` - everything | `catalyst`, `sql`, `varka-docs`, `docs` |
| a plan file only | `varka-docs` | `varka-docs` |
| the surface driver only | `root` - everything | `varka-bench` |
| a results file only | `varka-bench` | `varka-bench` |

Through the workflow's own queries, #234's files now answer `yarn: false`,
`kubernetes: false` and `varka-bench: false` where all three were true. What
stays true stays true honestly: `sql`, `sparkr`, `docker-integration-tests` and
`pyspark` are selected because they depend on `catalyst` in the module graph,
and a compiler change can break them.

**VARKA-94's open half is now provable.** "A bench-only change runs the bench job
alone" was unprovable while `dev/varka_bench_surface.sh` selected `root`; it
selects `varka-bench` alone.

## 7. Risks

* **A job that should have run and does not.** The map is widened, never
  narrowed: every path claimed here previously selected `root`, so the only
  change is from "everything" to "the module that owns the file". A file whose
  owner is wrong would under-test, which is why each claim above names the suite
  that reads the file rather than the directory it sits in.
