## 2. `positive`: why its coverage row declines, and what the census says

**The census** (`sql/varka/plans/m8/census.tsv`) is generated by `python3 dev/varka_census.py`
from Spark's function registry, from the hand-edited `sql/varka/plans/m8/census_curated.txt`
(one line per function in scope: its types, its result, the types fused today, the need, the
plan rows, a note) and from `sql/varka/coverage.json`. A type counts fused for a function only
where a coverage row holds a node of the function's class over an operand of that type; the
script fails a claim no row shows.

**Why `positive(i) + 1` declines.** Read from the code; the probe of the row's note at
`52bf5a99683` saw "no entry fused", which is what `VarkaCoverageSuite.declinedRows` prints for
any single entry that declines.

1. `UnaryPositive` is `RuntimeReplaceable` and its `replacement` is its child
   (`sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/arithmetic.scala`).
   Spark's optimizer replaces it (`ReplaceExpressions`), so no physical plan holds the node:
   `positive(x)` runs as `x`, fused wherever `x` is.
2. The coverage suite compiles a row's *analyzed* expression, not the optimized one
   (`VarkaCoverageSuite.expressionOf`). So it hands the compiler `Add(UnaryPositive(i), 1)`.
3. `VarkaNodeCompiler.intArith` asks `intOperand` for each side. `intOperand` takes a bare
   `IntegerType` column or literal as a leaf (`intLeaf`); anything else goes to `compileNode`.
4. No family claims `UnaryPositive`, so `compileNode` reaches `fallback`, which compiles a
   `RuntimeReplaceable` as its replacement: `compileNode(i)`.
5. `compileNode` has no leaf for a bare `INT` column: "`INT` has no value leaf by design" (row
   333's admission check). So `fallback` declines the column with the reason "non-date column
   of type int".

So the row's note is right that the compiler asks again for the child; it asks through
`compileNode`, which has no bare-int leaf, and not through the operand rule of the position the
node stood in. The census cannot credit the function another way: its rewrite map (`VIA` in
`dev/varka_census.py`) credits `ifnull` through `Coalesce`, the class it is rewritten to, and
`positive` is rewritten to no class at all.

    grep -n 'override lazy val replacement: Expression = child' sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/arithmetic.scala
    grep -n 'return compileNode(r.replacement(), inputs, literals, sink);' sql/catalyst/src/main/java/org/apache/spark/sql/catalyst/expressions/codegen/VarkaNodeCompiler.java

Each prints one line. **Only a JVM confirms the reason's text**; the command for the lead is
`dev/varka_emit.sh "positive(i) + 1" --columns i:int`, whose entry should read `ResidualOutput -
non-date column of type int` if the tool compiles the analyzed tree as the suite does.

**What the census says about it.** `positive` stays in scope and uncounted, as
`known_fp_normalized` is by the owner's answer of 30 October 2026 (its line in the curated
file): a function that leaves no node in a plan has nothing a coverage row can hold. Its nine
pairs (`TINYINT`, `SMALLINT`, `INT`, `BIGINT`, `FLOAT`, `DOUBLE`, `DECIMAL` and the two interval
types) stay unfused in the count, with this reason in the note. Question 1 of section 6 gives
the two other choices.

## 3. `ceil` and `ceiling` over the integral types

`Ceil` takes a `DOUBLE`, a `DECIMAL` or a `BIGINT` (`Ceil.inputTypes` in `mathExpressions.scala`),
so `ceil(i)` over an `INT` is `Ceil(Cast(i AS DOUBLE))`. `VarkaRoundingCompiler.floorOrCeil`
fuses it as the int widened to a `BIGINT`. The coverage row `ceil(i)` records its operand as
`Ceil:double`, the cast's type, so the census holds the claim as a derived one, marked `~`, and
its note quotes the row: `ceil` has had `int~` since row 344's part 344a1 (#1404). The row's
note, written on 20 November, says `ceil` has no credit for `int`; that is stale.

- **`ceiling` over `INT`: credited by this row.** `ceiling` registers the same builder as
  `ceil` (`expressionBuilder("ceiling", CeilExpressionBuilder, true)` in `FunctionRegistry.scala`)
  and the census checks both names against the class `Ceil` (`VIA`). So `ceiling` takes `int~`
  with the same quoted row, `ceil(i)`, and the script accepts it: checked on a copy (section 4).
- **`TINYINT` and `SMALLINT`, for both names: unbuilt, and the census says so.**
  `floorOrCeil` declines them by name: "floor or ceil over a cast from smallint to double, which
  needs the narrow load in a BIGINT kernel (row 344c)". The work is row 344's part 344b, which
  the owner's decision 1 moved to `m10/SCOPE.md` item 140 with `FLOAT` and `DOUBLE`. The note
  names that place.

    grep -n 'which needs the narrow load in a BIGINT kernel' sql/catalyst/src/main/java/org/apache/spark/sql/catalyst/expressions/codegen/VarkaRoundingCompiler.java
    awk -F'\t' '$1=="ceil" || $1=="ceiling" || $1=="positive" {print $1, $8}' sql/varka/plans/m8/census.tsv

The second prints `ceil int,bigint`, `ceiling bigint` and `positive` with nothing after it.
