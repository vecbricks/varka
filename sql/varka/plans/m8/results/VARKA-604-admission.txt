What ran: results/VARKA-604/Probe604.java, built by results/VARKA-604/build.sh and run by
results/VARKA-604/run.sh, three JVMs a mode at once. The probe calls the spike's split F loop
(VarkaDecimalRemainderSpikeBenchmark .loopRemainderFS, x % y) over a 4,096-row table of DECIMAL(38)
slots in Arrow's layout, a block at a time: tIn copies the block's x and y slots into two reused
split blocks (low words, then high words) by scalar moves, the loop runs over the blocks, and tOut
copies the result and the zero-divisor words back. tIn, tOut, the loop and the add loops are kept
out of line by compile commands, and the spike's bodies forced inline, as the spike's harness
requires. Each JVM primes the path with 20,000 calls, drives it for 8 s, then reads its own thread's
allocation over 256 drives of 4,096 rows and checks every row's answer and zero-divisor bit against
BigInteger.

Read:
1. The residual of VARKA-577.md 10.4's test of 7.4 is reproduced: 16 bytes a row at two lanes and
   12 at four, one long[L] a lane group, after vector code that profiles the shared templates
   over many species. The three plain add loops written here did not reproduce it (0 / 3); 10.4's
   add loops were not committed, so the polluter here is a stand-in, not theirs.
2. The engine's template warm-up removes it at blocks of 64 and 256 rows: 0 of 18 JVMs at two
   lanes and 0 of 3 at four, against 10 of 12 and 2 of 3 without it under the same polluter. It
   does so also when it runs after the polluter (mixed-late, 0 of 6), the order of a JVM whose
   other vector code runs before Varka's first kernel.
   10.4 left exactly this untested ("whether the 295 warm-up's template pre-warming protects a
   two-lane kernel is untested").
3. It does not at blocks of 1,024 rows: 3 of 3 keep 16 bytes a row with the warm-up, 32 without.
   So the block size matters here, which 10.4 did not see (it read 16 bytes a row at 64 and at
   1,024 without the warm-up); the arm takes the 64-row block.
   With the same 1,024-row transpose but the loop called once a 64-row sub-block, the warm-up
   leaves only the slices' 1.88 bytes a row, against 17.88 without it: so what matters is the
   rows the loop runs a call, not the transpose's size. Why a longer call keeps the array is not
   read here (no compile log was taken).
4. Every JVM's answers were exact.
