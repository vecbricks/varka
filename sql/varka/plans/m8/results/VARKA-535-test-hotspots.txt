# Two test hot spots (VARKA-535), 30 October 2026, laptop numbers

Two CPU hot spots that the suite profile (`m8/results/VARKA-suite-profile.txt`,
section 5, fixes 2 and 4) found in two catalyst suites, each
removed without changing an assertion or a test's coverage.

## 1. VarkaGroupingBoundSuite: one plan per call

`VarkaLoopEmitter.runsForTest` gave the runs of outputs from one start index and planned the
whole projection (`VarkaKernelPlan.of`) on every call, only to read the lane it is driven at;
`VarkaGroupingBound.runs`, its only caller, called it once per output, so a shape of n outputs
was planned n times for each of the suite's option sets. The profile sampled `VarkaKernelPlan.of`
at 29.8 s of the suite's 58.7 s at the defaults.

`runsForTest(outputs, options)` now returns the runs of every start: it plans once, keeps one
account of the outputs before the start that grows as the start advances (the per-start call
built the same account from scratch, adding the same outputs in the same order), and hands each
start a copy of its prefixes, as the per-start call did. `admit`, `closes`, `planOf` and the
emitter's own grouping walks are unchanged; only the test entry point and a private helper it
calls (`runsFrom`, the per-start loop moved out unchanged) differ.

Equality, checked side by side before the per-start method was removed: `VarkaGroupingBound.runs`
computed both the new answer and the per-start answer for every index and threw on any
difference (record equality, so the NaN predictions of unpriced runs compare equal). The suite
ran under it through `dev/varka_matrix.sh --config cse=false --module catalyst --suites
VarkaGroupingBoundSuite --jvm-arg -Dvarka.series.size=4`, which runs the defaults and cse=false:

  defaults   3 tests passed            13431 (shape, options) calls equal, 254442 runs compared
  cse=false  2 passed, 1 cancelled     8954 calls equal, 169628 runs compared
             (the cancelled test pins the defaults, as on master)

Production emission does not call `runsForTest`, and none of the code it shares with it changed.
`VarkaEmittedBytesSuite` ran on the after build at the defaults and passed its five byte checks
(its two audits cancel without their flag, as on master).

## 2. VarkaEmitterNarrowArithSuite: each output's lane once a batch

The stored narrow lane of `VarkaKernelChecks` read `root.laneType()`, which walks the root's
tree, on every row: in `got` for each fill's comparison and in `putOutput` and `sentinelOutput`
while seeding the output buffers, over batches of 2^24 rows. The profile sampled `laneType` and
its type switch at 6.1 s of the suite's 28.0 s.

The `Lane` interface's four output methods now take the root's lane beside the root, read once
per output by the caller (`runLoaded` before its row loop, `outputs` and `digest` once per output);
`outputs` also computes the sentinel once per output. The long lane still reads the root itself
(a `NarrowLane` root stores four bytes), so the root is passed as before. What is compared and
every message are unchanged.

## 4. The other lanes

The interface change reaches every lane of `VarkaKernelChecks`, and the mixed lane's per-row
`laneType` goes with it. On the final tree (whose fix differs from the timed after build only in
spelling three local variables' types instead of `var`), `dev/varka_matrix.sh --defaults --module
catalyst --jvm-arg -Dvarka.series.size=4` over `VarkaEmitterMixedLaneSuite` (the mixed lane),
`VarkaTimestampNtzCastSuite` (the long lane), `VarkaEmitterNarrowArithSuite` and
`VarkaGroupingBoundSuite` passed: 18 tests with 1 cancelled, 4, 49 with 19 cancelled, and 3. The
int lane's suites and every configuration are left to CI.
