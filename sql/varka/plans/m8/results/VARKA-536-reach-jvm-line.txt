# Why seven option configurations ran every sql test (VARKA-536), 30 October 2026: the reach
# record of option matrix run 40999948397 on the fork (head 3c09712f0d4, its Build 40979494508),
# and recordings of the sql Varka suites on the laptop (branch varka-536-reach-jvm-line on
# ef32e007d3a). Every count below the CI section is a laptop number.

The record in CI
  The run's artifact varka-option-matrix-reach is the six parts of the Build's three sql jobs,
  two JVMs each (--split 2). Five parts end with a JVM-wide line "*<TAB>*<TAB>-"; one, the
  first JVM of the third job (sql-0 of varka-scoped-junit-sql-3of3), names seven
  configurations: checkIntOverflow=false, denseValidityOnce=false, driverOutputTable=false,
  elideUnreadLocals=false, methodByteBudget=0, validityByBitmap=false, validityByWidth=false.
  VarkaTestReach.read joins every "*<TAB>*" line of the concatenated record into every test of
  every part, so one JVM's line made each of the seven run all 1687 recorded sql tests.
  The matrix report (ok tests, sql and catalyst together): the seven ran 2433 to 2515 ok tests
  (checkIntOverflow=false 2433, validityByWidth=false 2450, methodByteBudget=0 2485,
  driverOutputTable=false 2504, validityByBitmap=false 2514, denseValidityOnce=false 2515,
  elideUnreadLocals=false 2515); filtered ones far fewer (groupBudget=64 846,
  julianMap=false 1038, cse=false 1242).
  That JVM's JUnit reports name eleven suites. Ten have record lines; VarkaLiteralLiftSuite,
  the first to run (17:38:08), has none.

The cause
  The hypothesis first: VarkaVectorTemplateWarmup emits no kernel. It calls Vector API
  templates directly and never reaches VarkaLoopEmitter or VarkaCompileObserver, so it cannot
  reach the recorder. Ruled out.
  The emitter: VarkaLiteralLiftSuite is a plain SparkFunSuite. Its tests run
  VarkaArrowSource.LiftRule, which asks VarkaExpressionCompiler.compile whether each lifted
  entry fuses, and that compile emits kernels. ScalaTest's Runner builds every suite before it
  runs any, so a VarkaMatrixTests suite's constructor has already installed the recorder; the
  lift suite opens no window, so Recorder.note puts its compiles on the JVM-wide set.
  How it was found: a temporary print in Recorder.note (not committed) of the thread and stack
  of every compile noted outside every window.
    the eleven suites of that JVM, one JVM: 21 notes, all on thread
      ScalaTest-run-running-VarkaLiteralLiftSuite, from its test bodies (lines 50, 61, 70, 108),
      their union the seven configurations; the JVM-wide line names the seven
    all sql Varka suites, four JVMs (--split 4): 21 notes, the same thread and nothing else;
      one JVM-wide line names the seven, the other three are "-"
  Soundness of moving them: the lift rule only tests the compile's result for presence and
  keeps nothing, and VarkaExpressionCompiler.compile defines no class and fills no shape
  cache. So no later test reuses anything those compiles built. A test that meets the same
  IR is charged anyway, through its own compile, through producedBy, or through the shape
  cache's lookup, which reports every hit.

The fix
  VarkaLiteralLiftSuite mixes in VarkaReachWindow, a byte-identical copy of the trait on branch
  varka-518-catalyst-reach. The trait opens the suite's reach window around its run, so the
  compiles become the suite's own "VarkaLiteralLiftSuite<TAB>*" line. No test reads that line,
  since the suite has no test lines, and its tests still run under every configuration, as
  before. VarkaTestReach.java is not touched.

  The cache builds a shape only when it has not admitted that shape's key, so the probe lands
