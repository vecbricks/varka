  == build: sql's test classes, its test classpath and JVM options
  126 bins, the longest 480 s, 59882 s in all
where 41035158315's says:
  == the test classes of Build run 41022383513
  == the reach of Build run 41022383513: 1749 tests

So the 528 run found no Build archive. It compiled the classes itself (11.7 minutes instead of

## 2. Was it #1178's change?

The code change did not do it. #1178 (3875255ff86, 14 files) touches the harness classes,
VarkaHarnessStore, the workflows, varka_matrix.sh, varka_matrix_archive.sh and
varka_scoped_suites.sh. It touches neither VarkaTestReach nor the reach reading in
varka_matrix_bins.py. The third run 41062859573 (reach present, 1749 tests, 106 bins, 50394 s
planned) matches the first (1749 tests, 106 bins, 50387 s).

The branch's state did it: its Build had scope "spark", which skips the Varka-scoped jobs.
Without those jobs there is no classes archive, no reach record and no harness store. This will
recur on any Varka pull request that also touches a path outside Varka's scope (a workflow, a
Spark source). Its matrix then compiles for itself and runs unfiltered.

Caveat on the "clean comparison": 41062859573's head 202d0163b09 does NOT contain 3875255ff86
(git merge-base --is-ancestor says no). It is one more 481 commit, not master merged in, and
its Build 41059844622 uploaded no varka-harness-store-* artifact. No matrix has yet run on a
commit that contains #1178 and has a Varka-scoped Build, so the harness store's effect on the
matrix is still unmeasured. The plan-only branches' Builds at 13:01 UTC (41059826684,
41059829264, 41059860623) uploaded no reach or store. The fork's post-merge master Build of
3875255ff86 ("Build / Varka master after each merge (JDK 25)", 41062626402) did run the
Varka-scoped jobs. It uploaded the classes archive, three varka-matrix-reach-sql-* parts holding
1758 tests (against 1749 in Build 41022383513, which run 1 read) and varka-harness-store-sql-1of3
and -2of3 (6.4 MB and 4.7 MB; sql 3 of 3 wrote none). So #1178 leaves the record's size about
where it was (+9 tests), and a matrix dispatched on master at 3875255ff86 or later would be the
first to measure the store.

What #1178 adds or saves in the matrix, from the JUnit reports:
  VarkaHarnessParitySuite (new, 43 s at the defaults on the laptop): 0 runs in the matrix of
    41052708388: dev/varka_matrix.sh line 171 leaves it out ("checks that the answer harness
    plans as a session does, not an answer"), so it costs only the PR Build.
  VarkaHarnessStoreSuite: 49 runs, 13 s in all.
  Harness suites the store speeds up, run 1 (with reach): VarkaCoverageHarnessSuite 1035 s,
    VarkaTimeHarnessSuite 262 s, VarkaDifferentialHarnessSuite 133 s = 1430 s. At #1178's
    laptop ratio (58.3 s -> 15.6 s under cse=false) that is about 1000 JVM-s saved, about 8
    bin-minutes. The net effect on the matrix is small either way.

## Options, ranked by minutes saved on a typical run

1. Never let the matrix run without the Build's classes and reach. Against run 2 this saves 10.4
   minutes of build and 136 bin-minutes (4.5 minutes at 30 slots): floor 40.0 -> 25.0. It is
   safe because it is the matrix's normal path. Ways (a choice for the lead):
   (a) "Check changes" runs the sql Varka-scoped jobs and the classes job whenever Varka files
       changed, even when the scope is "spark". This costs those jobs' slots on such PRs.
   (b) The matrix's build job warns or fails at once when it would run without a reach record,
       so the dispatch is not wasted. This is the cheapest option and adds no CI work.
   (c) Dispatch the matrix only on a commit whose Build ran Varka-scoped. This is a rule, with no
       code.
2. Hold all 30 slots, with no bin-minute change: dispatch or admit the matrix only when no
   full-Spark Build is running. dev/varka_ci_admit.py already admits full-matrix Builds
   (--concurrent 2); it could also count the matrix. At 696 bin-minutes, this turns 35.8 into
   about 27. Saves about 9 minutes. Safe; nothing verified changes.
   Raising max-parallel to 40 when the fork is idle gives 17.4 + 1.8 + 2 = about 21 minutes,
   about 6 more, but it collides with the rule that concurrent runs fit in 40 together. Owner
   decision.
3. A reach record for catalyst's non-tree suites (GroupingBound, EmitterNarrowArith,
   Avx2Select, Variant, EmitterBool, EmitCost, ...: 28573 s, run whole under all 46
   configurations). The stated reason catalyst records nothing is the tree suites' kernel
   volume, which does not apply to these. If the record cut them as it cuts sql (sql
   configuration median 423 JVM-s against the defaults' 1071), 30 to 60% of 28573 s is 70 to 140
   bin-minutes, 2.3 to 4.7 minutes at 30 slots. ESTIMATE, not measured. It keeps the same
   contract as sql's record: a configuration skips only tests whose kernels it leaves
   unchanged. Two things to verify first: the cost of recording at the defaults in the catalyst
   PR jobs, and that these suites' tests map to kernels the way the sql ones do.
4. Packing: about 47 bin-minutes of lane imbalance and about 53 of per-bin setup. Packing lanes
   closer to the target (best fit instead of first fit, or units cut finer) might recover 20 to
   30 bin-minutes, about 1 minute. Fewer, longer bins would cut setup but lengthen the tail.
   Safe; small.
5. Let #1178's harness store take effect. It needs only a Varka-scoped Build of a commit that
   contains #1178. Estimated about 8 bin-minutes (0.3 minutes). Safe; already merged; unmeasured.
6. Fewer fuzz draws per configuration, or seeds split across configurations (the four fuzz
   suites are about 162 bin-minutes). This WEAKENS what each configuration verifies. Not
   recommended without the owner's decision.
7. The build-and-plan job is 1.3 to 1.7 minutes when it reuses the Build, so there is nothing to
   gain there. It costs 11.7 minutes only on the self-compile path, which option 1 removes.

Combined, 1 + 3 + 4 + 5 give about 696 - 105 - 25 - 8 = about 560 bin-minutes. At 30 slots that
is 18.7 + 1.8 + 2 = about 22.5 minutes. At the about 17 slots a full-Spark Build leaves, it is
33 + 3.8 = about 37 minutes, still a miss. Bin-minute cuts give headroom, but a reliable 30
minutes needs option 2 (slots) as well as option 1 (the record).

## 6. The rule the fix settled on

The first version of the fix ran the classes job and sql's three Varka jobs beside Spark's
module matrix when the change held "Varka code", a file test (modules.has_varka_code). A second
review of that fix found the test wrong both ways:
- Spark-only edits of the shared hooks (CodeGenerator, SQLConf, the Arrow serializer) change the
  kernels the suites emit, yet left no record.
- Files the suites read (sql/varka/coverage.json, plans/m8/casts.tsv, the census tables,
  plans/figures/*.py, dev/varka_matrix_shards.py) were classed as documents.
- CI tooling and fixtures (dev/varka_ci_ledger_fixtures/*, dev/varka_matrix_bins.py, ...) were
  classed as code.

The rule now: when the scope is "spark" and the change builds catalyst or sql
(dev/is-changed.py -m catalyst,sql, which follows the module graph, so a core change counts),
the Build runs the classes job and sql's three Varka jobs beside the module matrix, and not
catalyst's three. A Spark change that builds neither (Python, docs/ pages, another module) runs
none. has_varka_code and its list of record files are gone. In such a Build:
- The four jobs need `admit`, so a run labelled ci-hold holds them, and they start when the run
  is admitted. A run that skips `admit` (Varka-scoped, documents only) runs them at once.
- They save no dependency cache, no per-run `varka-scoped-times-...-<run_id>` cache entry and
  no `varka-compile-state` artifact: a Spark branch would add its own entries to the fork's
  cache quota, and its compile state must never become another pull request's base.
- The admit job admits runs as before (--concurrent 2). A later review proposed admitting a run
  with the Varka jobs alone, since one that compiles clean may hold about 24 slots at its fan-out
  (section 5) and two of them would pass the fork's 40; that rule was dropped to keep the fix
  small, and the overlap is left unmeasured.

The option matrix's lookup (dev/varka_matrix_reuse.py) waits for such a Build: up to 30 minutes
while it is still queued in its admit job, two minutes for a classes job not yet listed after
the precondition and the admit (succeeded or skipped), and up to 10 minutes for the reach record,
ending that wait as soon as one sql job has failed and retrying a failed API poll three times.
Each way it ends without the record names the reason and what to do in a warning.

The cost it leaves: both the module matrix's sql shards and the Varka sql jobs run the sql Varka
suites in such a Build. Spark's build has no suite-name filter to drop them from the module
matrix, and the module matrix splits sql by ScalaTest tags while the Varka jobs pick suites by
name (plus ArrowCachedBatchSerializerSuite), so a name filter could miss or over-cut. Its cost is
the Varka jobs themselves, from the two Builds in section 5: sql's three took 8.2 to 10.2 minutes
each and the classes job 3.9 to 4.0, about 31 duplicate job-minutes per spark-scope Build.

A later row could remove them: make the module matrix's sql shards write the reach record and
the harness store themselves (VARKA_REACH_RECORD, VARKA_HARNESS_STORE) and upload them as the
Varka sql jobs do, so the option matrix reads those and the extra sql jobs go away; the classes
job stays.
