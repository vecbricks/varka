## 1. Core Mission

Eliminate runtime compilation overhead (string parsing, AST generation) and unlock SIMD hardware capabilities (AVX-512, ARM SVE) without breaking compatibility or stability. The system must be a **drop-in, zero-risk replacement** for the existing engine.

---

## 2. Architectural Principles (Non-Negotiable)

1. **Zero-Risk Fallback (The "Ghost" Janino):** The system never pre-generates Janino strings. If bytecode generation fails, it *lazily* generates the Janino string, compiles it, caches it, and retries. The user job never crashes.
2. **Granular Degradation:** Failure of a single column or complex operation does NOT revert the entire `WholeStageCodegen`. The generated class will use SIMD for the supported columns and scalar loops for the unsupported ones within the same method.
3. **Metaspace Safety:** Generated classes are loaded via a dedicated `VarkaClassLoader` scoped to the Spark task, ensuring classes are unloaded upon task completion, preventing long-term Metaspace bloat.
4. **No "Dual Generation" Overhead:** On the happy path, we generate zero strings for the execution logic. The Java string representation is created *only* during the fallback path.
5. **Arrow-Native Memory:** Data comes from `ArrowColumnarBatch`. We map `ArrowBuf` directly to Panama `MemorySegment` (zero-copy, off-heap). We never convert to heap objects for processing.
6. **Hardware Alignment:** Memory buffers are 64-byte aligned (cache-line friendly) to maximize CPU prefetching.

## 4. Data Model: VarkaMorsel (Arrow Integration)

The engine operates on `ArrowColumnarBatch` vectors. We map the buffers to memory segments.

**Mapping Process:**
```java
// DateType Column
ArrowBuf dataBuffer = vector.getDataBuffer();   // Ints (4 bytes each)
ArrowBuf validityBuffer = vector.getValidityBuffer(); // Bitmask (1 bit per row)

MemorySegment dataSeg = MemorySegment.ofAddress(dataBuffer.memoryAddress())
    .reinterpret((long) rowCount * 4L);
MemorySegment validitySeg = MemorySegment.ofAddress(validityBuffer.memoryAddress())
    .reinterpret((long) (rowCount + 7) / 8L);
```

**Buffer Rules:**
- **Validity Buffer:** 1 bit per row (byte-aligned for SIMD loads).
- **Data Buffer:** Primitive layout (e.g., `JAVA_INT` for dates).
- **Alignment:** Buffer start addresses must be 64-byte aligned (guaranteed by Arrow's allocator).

## 5. The 3-Tier Execution Pipeline (Refined)

- **Tier 1 (Caching):** Structural hash of the Catalyst plan. Constants (like `days=5`) are passed as runtime arguments, not inlined into the plan hash.
- **Tier 2 (MethodHandles - RESTRICTED):** Only used for external Vectorized UDFs (user-provided lambdas). Core Catalyst expressions bypass this completely to avoid C2 inlining depth limits.
- **Tier 3 (Class-File API - PRIMARY):** The main workhorse.
  - **NOP Fast Path:** If the generated bytecode snippet fits the adaptive threshold (see Section 6), `System.arraycopy` overrides pre-allocated NOP slots in a template class.
  - **Class Rebuild Slow Path:** If the snippet is too large, the engine fully rebuilds the class.

## 6. Critical Configuration Flags

| Config Key | Default | Description |
| :--- | :--- | :--- |
| `spark.sql.codegen.varka.enabled` | `true` | Master switch for the engine. |
| `spark.sql.codegen.varka.patch.threshold` | `64` | Max bytecode size for NOP Fast Path (bytes). |
| `spark.sql.codegen.varka.fallback.ghost.enabled` | `true` | Enable lazy Janino generation on failure. |

**Why 64 bytes and not 128?** Empirical data shows that simple vectorized operations with mask handling easily exceed 80 bytes. A conservative threshold ensures the Fast Path is actually hit reliably, preventing unpredictable slowdowns for slightly complex queries.

We are currently implementing the **Date/Time MVP**.

**Supported Expressions:**
- `DateAdd(startDate: Date, days: Integer) -> Date` (SIMD Int Addition).
- `DateSub(startDate: Date, days: Integer) -> Date` (SIMD Int Subtraction).
- `DateDiff(endDate: Date, startDate: Date) -> Integer` (SIMD Int Subtraction).

**Explicitly OUT OF SCOPE (MVP):**
- `CalendarInterval` (months, years). We strictly process integer day offsets.
- Strings, Decimals, Complex Nested Types.

## 8. Component Layout & Implementation Hints

### 8.1. Isolated Java Engine (Package: `org.apache.spark.sql.varka.vector`)
- **File:** `DateVectorOps.java`
- **Methods:** `vectorAddDays`, `vectorDateDiff`.
- **Implementation Pattern:** Load `MemorySegment` via `ofAddress`. Use `SPECIES.loopBound(length)` for the vector loop, and a **strict scalar tail** for the remainder (avoids unaligned memory exceptions).
- **Validity Mask Handling:** For `DATEDIFF`, we must combine two validity masks using `VectorMask.and()` to ensure we don't read null values from either column.

### 8.2. ClassLoader (Package: `org.apache.spark.sql.varka.execution`)
- **File:** `VarkaClassLoader.scala`
- **Lifecycle:** Instanced per `WholeStageCodegen` task. Bound to `TaskContext`.
- **Release:** Called in `TaskCompletionListener` to clear references and allow GC.

### 8.3. Catalyst Hooks (Scala)

> **Status:** this hook shipped in milestone 1 and was retired in task 17 once the
> fused loop had replaced it. Eligibility and compilation live in
> `VarkaExpressionCompiler`, which the columnar rule and the evaluator share; the
> expressions carry no Varka trait and `genCode` is untouched.

- **Trait:** `ClassFileCodegenSupport`.
- **Patched Expressions:** `DateAdd`, `DateSub`, `DateDiff`.
- **Key Action:** Override `genCode`. We **do not** call `doGenCode`. Instead, we append the expression to a list inside `CodegenContext` for later bytecode assembly.
- **Bytecode Emission:** Use `invokestatic` to call `DateVectorOps.vectorAddDays`. The method signature requires the exact primitive stack order.

### 8.4. CodeGenerator Assembly (Scala)
- **File:** `CodeGenerator.scala`
- **Hook:** In `doCompile`, check `ctx.isClassFileGenEligible`.
- **Assembly:** If eligible, assemble the bytecode using the Class-File API. If an exception occurs, generate the Janino string *at this moment* (Ghost fallback) and cache it.

## 9. Testing Strategy

1. **Differential Testing (Correctness):**
   - Run the same query with `spark.sql.varka.enabled=false` and `true`.
   - Assert `checkAnswer` passes.
   - Use the built-in Spark `QueryTest` infrastructure.

2. **Performance Benchmarking (JMH):**
   - Isolated benchmark for `DateVectorOps` (Java side) comparing against scalar Java loops.
   - Integrated benchmark (Spark side) comparing Varka against Janino for 1k to 10M row datasets.
   - Metrics: Generation Time (microseconds), Throughput (rows/sec).

3. **Metaspace Stress Test:**
   - Run 10,000 unique `SELECT DATE_ADD(...)` queries in a loop.
   - Monitor Metaspace usage via JVM MXBeans. Ensure usage plateaus (unloading works).

## 11. Risk Matrix (Active Concerns)

| Risk | Trigger | Mitigation |
| :--- | :--- | :--- |
| **C2 Inlining Limit** | Deep `MethodHandle` chains. | **Action:** Restrict MethodHandles to UDFs only. For internal logic, always use Class-File API. |
| **Metaspace OOM** | High query diversity generating too many classes. | **Action:** Enforce `VarkaClassLoader` release. Add `-XX:MaxMetaspaceSize=512M` as a safety net. |
| **Fast Path Failure** | Generated expression > 64 bytes. | **Action:** Log warning, use Slow Path (Class rebuild). Ensures no correctness failure, only slight latency increase. |
| **Arrow Format Changes** | Spark upgrades change Arrow buffer layout. | **Action:** Isolate buffer extraction logic in `VarkaMorsel.extractSegments()`. |
